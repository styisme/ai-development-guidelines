## Why This Spec Exists

AI can now write code that compiles, runs, and ships. The question is no longer *whether* AI can write it, but:

- Who is **accountable** when something breaks;
- Which parts were generated and which were reviewed — **nobody can tell**;
- High-risk features slip into production because AI wrote them — **nobody stops them**;
- Projects claim "AI-assisted development" with **no verifiable disclosure standard**.

This spec defines a minimal set of conventions: **humans own decisions and acceptance, AI generates, and generated content must be verifiable, disclosable, and accountable.**

This spec does not rank AI tools, nor does it mandate a specific model.

---

## Guiding Principles

1. **Humans are accountable.** AI is neither author nor responsible party.
2. **Generated is not the same as usable.** Code that hasn't been compiled, reviewed, and verified is not done.
3. **Review rigor scales with privilege.** The closer code is to auth, filesystem, command execution, or release pipelines, the stricter the review.
4. **Secure and off by default.** High-risk capabilities are disabled by default; enabling them requires explicit confirmation and a record.
5. **Disclose truthfully.** Write "about 80%" rather than "entirely AI-generated" while offering no verification trail.

## The Spec

The key words **MUST**, **SHOULD**, and **MAY** are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

### 1. Accountability

1.1 A project **MUST** designate at least one human maintainer responsible for merges and releases.  
1.2 Decisions to merge, release, delete data, or change permissions **MUST** be made by a human and **MUST NOT** be automated by AI.  
1.3 A project **SHOULD** state in its documentation that AI participates in generation while humans own acceptance.

### 2. Scope of Use

2.1 The following **MAY** be generated directly by AI, subject to compilation and basic review: boilerplate, UI layouts, styles, documentation drafts, comments, test drafts, and build scripts.  
2.2 The following **MUST** receive line-by-line human review: authentication and sessions, encryption and certificates, path and sandbox validation, protocol parsing, command execution, database migrations, and CI/CD secrets and release scripts.  
2.3 A project **MUST NOT** submit real secrets, certificates, tokens, or user data to public AI services.  
2.4 High-risk capabilities (root access, full-disk access, remote command execution, self-destruct, tunneling, etc.) **MUST NOT** be enabled by default and **MUST** be called out separately in security documentation.  
2.5 A project **MUST NOT** overstate or understate its AI involvement in disclosure documents.

### 3. Generation and Review

3.1 Each AI generation **SHOULD** be grounded in explicit context: goals, constraints, target platform, relevant files, and error logs.  
3.2 AI-generated code **MUST** be reviewed by a human before reaching the main branch.  
3.3 Review **SHOULD** cover at minimum: logical correctness, error handling, dependency necessity, whether platform APIs actually exist, and license compatibility.  
3.4 Large generated changes **SHOULD** be committed separately to ease tracing and rollback.  
3.5 Commit messages **MAY** be tagged `ai-assisted`, or the PR description **MAY** state the scope of AI involvement.

### 4. Verification

4.1 AI-generated code **MUST** compile at least once on the target platform.  
4.2 Changes involving platform APIs, permissions, UI, background survival, or networking **MUST** be verified on real devices or real environments.  
4.3 Core logic (parsers, path validation, authentication, chunked uploads, etc.) **SHOULD** have repeatable tests.  
4.4 "The AI said it's fine" **does not** constitute verification.  
4.5 After trimming, porting, or refactoring, a full regression **SHOULD** be performed.

### 5. Disclosure

5.1 A project **SHOULD** provide an AI disclosure file in the repository (recommended: `AI_DISCLOSURE.md`).  
5.2 Disclosure **MUST** include: the scope of AI involvement, the work humans performed, known limitations and risks, and licensing terms.  
5.3 Disclosure **MUST** be updated when: involvement changes materially, a new high-risk module is added, a new branch or port is created, or a major version is released.  
5.4 Disclosure **SHOULD** include a last-updated date.  
5.5 The disclosure file **MUST NOT** substitute for security documentation; high-risk capabilities **MUST** be documented separately.

### 6. Security and Compliance

6.1 Secrets and certificates **MUST** be injected via secrets stores or environment variables and **MUST NOT** enter the repository.  
6.2 Before adopting an AI-suggested third-party dependency, a project **SHOULD** assess its license, size, maintenance status, and security record.  
6.3 Generated audio, images, and text **MUST** carry a notice that users must comply with the relevant service terms and copyright requirements.  
6.4 Self-signed certificates, string blacklists, and client-side validation **MUST NOT** be described as "security-audited."

### 7. Documentation and Traceability

7.1 Documentation **SHOULD** accurately reflect the current code and **MUST NOT** describe planned features as shipped.  
7.2 The version number **SHOULD** have a single source of truth (e.g., `CHANGELOG.md`) injected by CI.  
7.3 Branches, lite editions, and ports **MUST** document their inheritance relationship with upstream.  
7.4 AI-generated Markdown **SHOULD** be manually checked for branch names, repository links, and relative paths.

## AI Disclosure Template

New projects can copy the following into `AI_DISCLOSURE.md`:

```markdown
# AI Disclosure

This project ({{project name}}) used large language models during {{development/refactoring/porting/trimming}}.

**Core statement: roughly {{percentage}} of the code was generated directly by AI; human developers handled {{product definition, review, testing, acceptance, and release}}.**

## Where AI Was Involved
- `{{file or module}}`: {{what was generated and why}}

## What Humans Did
- {{requirements / architecture decisions / build debugging / on-device testing / final acceptance}}

## Known Limitations
1. {{AI cannot run on real hardware; platform differences require human verification}}
2. {{platform API changes, edge cases, security risks, etc.}}

## License
This project is released under {{license}}.
```

## FAQ

**Does the AI percentage need to be exact?**  
No. It should be conservative and honest, and state the basis (by line, by module, or by feature).

**Do small projects need disclosure too?**  
Recommended. Disclosure is cheap; being unable to explain what happened is expensive.

**Can AI-generated code be used commercially?**  
It depends on the model terms, dependency licenses, and the project license. This spec offers no legal advice; audit before commercial use.

**Can a human be accountable without writing a single line?**  
Yes, provided the human performed requirements definition, review, verification, and release decisions. Accountability comes from decisions and acceptance, not keystrokes.

**Can AI-written docs be published directly?**  
Yes, but a human should verify version numbers, links, branch names, and feature descriptions.

2. Link to it from `README.md` and `CONTRIBUTING.md`;
3. Create `AI_DISCLOSURE.md` using the [template](#ai-disclosure-template);
