## 为什么要写这份规范

AI 已经能写出可编译、可运行、甚至可发布的代码。问题不再是“AI 能不能写”，而是：

- 出了事故，**谁负责**；
- 代码里哪些是生成的、哪些被审阅过，**说不清**；
- 高风险功能被 AI 顺手带进生产，**没人拦**；
- 对外宣称“AI 辅助开发”，但**没有可核对的披露口径**。

本规范给出一套最小约定：**人类负责决策与验收，AI 负责生成，生成内容必须可验证、可披露、可追责。**

本规范不评价 AI 工具优劣，也不规定你必须用哪个模型。

---

## 指导原则

1. **人类是责任主体。** AI 不是作者，也不是责任人。
2. **生成不等于可用。** 没有编译、没有审阅、没有验证的生成代码，不算完成。
3. **风险与权限成正比。** 越接近鉴权、文件系统、命令执行、发布流程，审阅要求越高。
4. **默认安全，默认关闭。** 高危能力默认不开启，开启必须显式确认并留下记录。
5. **披露要真实。** 宁可写“约 80%”，不要写“全部由 AI 完成”却拿不出验证过程。

## 规范

以下关键词按 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 理解：**必须（MUST）**、**应当（SHOULD）**、**可以（MAY）**。

### 1. 责任归属

1.1 项目**必须**指定至少一名人类维护者，对合并与发布负责。  
1.2 合并、发布、删除数据、变更权限等决策**必须**由人类做出，**不得**由 AI 自动执行。  
1.3 项目**应当**在文档中说明：AI 参与生成，人类负责验收。

### 2. 使用边界

2.1 以下内容**可以**由 AI 直接生成，但仍需编译与基本审阅：样板代码、UI 布局、样式、文档草稿、注释、测试草稿、构建脚本。  
2.2 以下内容**必须**由人类重点逐行审阅：鉴权与会话、加密与证书、路径与沙箱校验、协议解析、命令执行、数据库迁移、CI/CD 密钥与发布脚本。  
2.3 项目**不得**将真实密钥、证书、Token、用户数据提交给公开 AI 服务。  
2.4 高危能力（Root、全盘访问、远程命令、自毁、内网穿透等）**不得**默认开启，且**必须**在安全文档中单独警告。  
2.5 项目**不得**在披露文档中虚报或瞒报 AI 参与比例。

### 3. 生成与审阅

3.1 每次 AI 生成**应当**基于明确的上下文：目标、约束、目标平台、相关文件与错误日志。  
3.2 AI 生成代码**必须**经过人类审阅后才能进入主分支。  
3.3 审阅**应当**至少覆盖：逻辑正确性、异常处理、依赖必要性、平台 API 是否真实存在、许可证是否兼容。  
3.4 大块生成内容**应当**独立提交，便于回溯与回滚。  
3.5 提交信息**可以**标注 `ai-assisted`，或在 PR 描述中说明 AI 参与范围。

### 4. 验证

4.1 AI 生成代码**必须**在目标平台完成至少一次编译。  
4.2 涉及平台 API、权限、UI、保活、网络的改动**必须**在真实设备或真实环境验证。  
4.3 核心逻辑（解析器、路径校验、鉴权、上传合并等）**应当**有可重复执行的测试。  
4.4 “AI 说没问题”**不构成**验证结论。  
4.5 裁剪、移植、重构后**应当**执行一次完整回归。

### 5. 披露

5.1 项目**应当**在仓库中提供 AI 生成声明文件（推荐 `AI_DISCLOSURE.md`）。  
5.2 披露**必须**包含：AI 参与范围、人类负责的工作、已知局限与风险、许可说明。  
5.3 出现以下情况时**必须**更新披露：参与比例明显变化、新增高风险模块、新增分支或移植版、发布大版本。  
5.4 披露**应当**注明最后更新日期。  
5.5 披露文件**不得**替代安全文档；高危能力**必须**另有安全说明。

### 6. 安全与合规

6.1 密钥与证书**必须**通过 Secrets 或环境变量注入，**不得**进入仓库。  
6.2 引入 AI 建议的第三方依赖前，**应当**评估许可证、体积、维护状态与安全记录。  
6.3 生成的音频、图像、文本等内容，**必须**提示使用者遵守对应服务条款与版权要求。  
6.4 自签证书、字符串黑名单、前端校验等**不得**被描述为“已安全审计”。

### 7. 文档与追溯

7.1 文档**应当**准确反映当前代码，**不得**把计划中写成已支持。  
7.2 版本号**应当**有唯一来源（如 `CHANGELOG.md`），并由 CI 注入。  
7.3 分支、精简版、移植版**必须**说明与上游的继承关系。  
7.4 AI 生成的 Markdown **应当**人工核对分支名、仓库链接与相对路径。

## AI 生成声明模板

新项目可以直接复制以下模板到 `AI_DISCLOSURE.md`：

```markdown
# AI 生成声明

本项目（{{项目名称}}）在{{开发/重构/移植/精简}}过程中使用了大型语言模型辅助生成。

**核心声明：约 {{比例}} 的代码由 AI 直接输出；人类开发者负责{{产品定义、审阅、测试、验收与发布}}。**

## AI 参与的部分
- `{{文件或模块}}`：{{生成内容与作用}}

## 人类负责的工作
- {{需求定义 / 架构决策 / 编译排雷 / 真机测试 / 最终验收}}

## 已知局限
1. {{AI 无法真机运行，平台差异依赖人类验证}}
2. {{平台 API 变更、边缘场景、安全风险等}}

## 协议
本项目遵循 {{许可证}}。
```

## 常见问题

**AI 生成比例必须精确吗？**  
不必精确到个位，但应当保守真实，并说明统计口径（按行、按模块或按功能）。

**小项目也需要披露吗？**  
建议需要。披露的成本很低，而“出问题时说不清”的成本很高。

**AI 生成代码可以商用吗？**  
取决于模型条款、依赖许可证与项目许可证。本规范不提供法律意见，商用前建议自行审计。

**人类没有改一行代码，也能算人类负责吗？**  
能，前提是人类完成了需求定义、审阅、验证与发布决策。责任来自决策与验收，不来自敲键盘。

**AI 写的文档可以直接发布吗？**  
可以，但应当人工核对版本号、链接、分支名与功能描述。

## 采用本规范

在你的项目中：

1. 将本文件复制为 `docs/AI-DEVELOPMENT-GUIDELINES.md`；
2. 在 `README.md` 与 `CONTRIBUTING.md` 中链接本规范；
3. 按[模板](#ai-生成声明模板)创建 `AI_DISCLOSURE.md`；
4. 在 PR 模板中加入“已说明 AI 参与程度”“已在目标平台编译”“安全敏感代码已审阅”三项检查。
